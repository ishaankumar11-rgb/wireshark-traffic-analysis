# Wireshark Traffic Analysis Report

## 1. Scope and authorization
Traffic from my own Kali VM only, generated by me in a lab. Destination: example.com (a public documentation domain) and 8.8.8.8 (ICMP ping).

## 2. Capture summary
- 51 packets, 6317 bytes
- IPv4: 22 packets (DNS 8, ICMP 8, DHCP 2, mDNS 4)
- IPv6: 23 packets (TCP 13, ICMPv6 6, mDNS 4)
- ARP: 6 packets
Source: `evidence/protocol_hierarchy.txt`

## 3. Findings
| # | Finding | Severity | Evidence |
|---|---------|----------|----------|
| 1 | HTTP is unencrypted: the full request (`GET / HTTP/1.1`, `Host`, `User-Agent: curl/8.21.0`) and response (`200 OK`, headers, HTML) are readable in plain text | Low in this lab, High for real logins | `evidence/http_stream.txt` |
| 2 | DNS queries and answers go over UDP port 53 to the local resolver in plain text, so anyone on the network path can see which names were looked up | Low | `screenshots/01_dns.png` |
| 3 | The VM requested both A and AAAA records, and `curl` connected to example.com over IPv6 | Informational | `evidence/tcp_stream0.txt` |
| 4 | Normal TCP lifecycle: SYN, SYN/ACK, ACK, request, response, FIN/ACK teardown | Informational | `evidence/tcp_stream0.txt` |
| 5 | Some TCP segments arrived out of order (packets 31 and 33), causing a duplicate ACK; no data was lost | Informational | `evidence/tcp_stream0.txt` |
| 6 | Background broadcast noise (mDNS, ARP, DHCP) reveals device presence on the local network | Informational | `evidence/protocol_hierarchy.txt` |

## 4. Recommendations
- Use HTTPS (TLS) for all web traffic; a plain HTTP request exposes everything to anyone who can capture it.
- Use encrypted DNS (DNS over HTTPS or DNS over TLS) where possible.
- On untrusted networks, use a VPN.

## 5. Limitations
- Short capture (51 packets) from one VM on one network.
- The traffic was self-generated, so this is not a real incident investigation.
- HTTPS traffic was not analysed (it would need TLS keys).
- Severity ratings are my own judgement for a lab setting, not a formal scoring.
